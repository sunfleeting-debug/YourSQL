# 页式存储系统设计与实现说明

## 1. 文档目的

本文档说明当前 MiniSQL 页式存储系统的设计和代码实现，帮助负责存储模块的开发人员快速理解：

- 数据库文件如何划分为页面
- 页面内部如何组织记录
- 页面如何分配、释放和复用
- 缓冲池如何管理内存中的页面
- 表数据如何映射到页面链表
- Catalog 如何通过同一套页式存储机制持久化
- 当前实现已经满足什么要求，以及还存在哪些边界问题

本文档描述的是当前代码的实际行为，代码位置以 `database_system/` 为根目录。

## 2. 总体架构

页式存储系统的存储核心只包含三个文件。`engine/` 下的 `storage_engine.py`、`record.py` 和 `catalog_manager.py` 属于上层适配代码，不纳入页式存储核心，也不作为第四个存储模块文件。

```text
┌──────────────────────────────────────────────┐
│ TableHeap / CatalogManager（engine 层）        │
│ 表数据页链表、记录插入、扫描、删除、回收       │
└──────────────────────┬───────────────────────┘
                       │ fetch_page / unpin / new_page
┌──────────────────────▼───────────────────────┐
│ BufferPoolManager                            │
│ 固定帧缓冲池、pin、dirty、LRU/FIFO、刷盘、淘汰 │
└──────────────────────┬───────────────────────┘
                       │ read_page / write_page
┌──────────────────────▼───────────────────────┐
│ DiskManager                                  │
│ 数据库文件、元数据页、页分配、空闲页链表       │
└──────────────────────┬───────────────────────┘
                       │
                 database file
```

对应代码：

| 层次 | 文件 | 主要职责 |
|---|---|---|
| 存储核心 | `storage/page.py` | 页头、槽位目录、页内记录和页编码校验 |
| 存储核心 | `storage/file_manager.py` | 超级块、固定大小页文件、页分配和回收 |
| 存储核心 | `storage/buffer.py` | 缓冲池、pin/dirty、替换、刷盘、统计和事件日志 |
| 上层适配 | `engine/storage_engine.py` | 将一张表组织成页面链表，提供行级读写 |
| 上层适配 | `engine/record.py` | Row 与页内二进制记录之间的转换 |
| 上层适配 | `engine/catalog_manager.py` | 将系统目录保存为特殊表 |

核心设计原则是：上层不直接操作文件偏移，而是通过页号访问页面；需要内存中的页面时通过缓冲池获取，修改后通过 dirty 标记和刷盘持久化。

## 3. 数据库文件和页面编号

### 3.1 文件布局

数据库文件被视为一个固定大小页面的数组：

```text
文件偏移 0              4096              8192
       ┌────────────────┬─────────────────┬─────────────────┐
       │ page 0         │ page 1          │ page 2          │ ...
       │ 元数据页       │ 数据页/目录页    │ 数据页/目录页    │
       └────────────────┴─────────────────┴─────────────────┘
```

当前页面大小由 `PAGE_SIZE` 定义为 4096 字节。页号与文件偏移的关系是：

```text
page_offset = page_id × PAGE_SIZE
```

页号 0 保留为元数据页，普通数据页从页号 1 开始。`INVALID_PAGE_ID = -1` 表示不存在下一页或尚未分配页面。

实现位置：[`storage/file_manager.py`](../database_system/storage/file_manager.py)。

### 3.2 元数据页格式

当前磁盘格式版本为 `2`。元数据页前 28 字节采用小端格式 `<8sIIIii`：

| 偏移 | 大小 | 字段 | 作用 |
|---:|---:|---|---|
| 0 | 8 | magic | 判断文件是否为 MiniSQL 数据库 |
| 8 | 4 | version | 文件格式版本 |
| 12 | 4 | page_size | 页面大小，当前为 4096 |
| 16 | 4 | page_count | 文件当前页面总数 |
| 20 | 4 | free_list_head | 空闲页链表头页号 |
| 24 | 4 | catalog_root | 系统目录根页号 |

新数据库文件创建时，`page_count = 1`，表示文件目前只有元数据页；空闲链表头和 Catalog 根页均为 `-1`。

打开已有文件时，系统读取并检查 magic、version、page_size 和文件长度。如果元数据损坏、页面数据不足、空闲链表成环或格式版本不支持，则抛出 `StorageError`。本次重构允许破坏旧数据文件，不承诺旧文件格式兼容。

## 4. 页面内部结构

### 4.1 槽位页布局

当前数据页使用“页头 + 槽位目录 + 空闲区 + 记录区”的 Slotted Page 结构：

```text
低地址                                                            高地址
┌──────────────┬────────────────────┬──────────────┬──────────────┐
│ 页头 16 字节  │ 槽位目录 4×N 字节   │    空闲空间    │ 记录区        │
└──────────────┴────────────────────┴──────────────┴──────────────┘
                                                         ▲
                                               记录从页尾向前生长
```

页头字段如下：

| 偏移 | 大小 | 类型 | 字段 | 说明 |
|---:|---:|---|---|---|
| 0 | 1 | uint8 | `page_type` | 数据页、Catalog 页等 |
| 1 | 1 | uint8 | `flags` | 当前保留 |
| 2 | 4 | int32 | `next_page_id` | 同一张表的下一页 |
| 6 | 2 | uint16 | `num_slots` | 槽位目录项数量 |
| 8 | 2 | uint16 | `free_pointer` | 记录区当前起始位置 |
| 10 | 6 | bytes | reserved | 预留空间 |

每个槽位目录项占 4 字节：

```text
offset: uint16   记录在页内的起始位置
length: uint16   记录长度
```

槽位号是记录的页内逻辑标识。一个记录的物理地址由 `(page_id, slot_id)` 组成，代码中对应 `RowId`。

### 4.2 页面空间管理

记录区从页尾向低地址增长，槽位目录从页头向高地址增长。两者相遇时页面没有足够空间。

可用空间大致计算为：

```text
free_space = free_pointer
           - (HEADER_SIZE + SLOT_SIZE × num_slots)
           - 新槽位所需空间
```

如果已经存在被删除的槽位，则可以复用槽位目录项，不需要增加新的槽位空间。

这种设计有两个好处：

1. 记录长度可以变化，槽位只保存记录位置和长度。
2. 删除记录后，记录的物理地址不会因为其他记录移动而改变。

当前实现不会整理页内碎片。删除记录只把槽位设置为 `(offset=0, length=0)`，原记录占用的记录区空间不会立即回收。

## 5. 页面对象的操作模型

页面对象由 `Page` 类表示，持有：

```python
page_id       # 页面编号
data          # 长度固定为 PAGE_SIZE 的 bytearray
pin_count     # 当前被引用的次数
dirty         # 页面是否被修改但尚未刷盘
```

`pin_count` 和 `dirty` 是保留的兼容字段，真正的引用计数、淘汰和刷盘决策由 `BufferPoolManager` 负责。`Page.encode()` 将内存页校验后编码为固定大小字节，`Page.decode()` 负责从固定大小字节恢复页对象；页层不依赖 SQL 类型。

### 5.1 页面初始化

`Page.init()` 会清空整个页面，并设置：

- 页面类型
- 下一页为 `INVALID_PAGE_ID`
- 槽位数量为 0
- `free_pointer = PAGE_SIZE`

新建的数据页由缓冲池创建后标记为 dirty，等待刷盘。如果缓冲池没有可用帧但调用方仍持有 pinned 页面，`new_page_unpinned()` 会把新页直接初始化并写入磁盘，保证单帧缓冲池也能完成表页扩展。

### 5.2 插入记录

插入过程如下：

```text
1. 计算二进制记录长度
2. 查找第一个已删除槽位
3. 如果没有可复用槽位，则新增槽位目录项
4. 检查页内剩余空间
5. free_pointer 向低地址移动
6. 将记录写入新的记录区位置
7. 更新槽位 offset/length
8. 返回 slot_id
```

记录过大或页面空间不足时抛出 `StorageError`。

### 5.3 读取、删除和更新

- `get_record(slot_id)`：根据槽位读取记录；无效槽位或已删除槽位返回 `None`。
- `delete_record(slot_id)`：把槽位清空，形成可复用槽位。
- `update_record(slot_id, data)`：只支持原地更新，新的二进制记录不能比原记录更长；较短内容用 0 填充。

当前 SQL 执行器的 UPDATE 并不直接依赖页内原地更新，而是删除旧记录后重新插入新记录。

## 6. 磁盘管理器

`DiskManager` 负责数据库文件和页面之间的直接转换。

### 6.1 页面读取和写入

`read_page(page_id)`：

1. 检查页号必须大于 0 且小于 `page_count`
2. 定位到 `page_id × PAGE_SIZE`
3. 读取固定的 4096 字节
4. 检查页面不在空闲页集合中
5. 长度不正确时抛出错误

`write_page(page_id, data)`：

1. 检查页号范围
2. 检查数据长度必须正好为 4096 字节
3. 写入对应文件位置
4. 拒绝把空闲页标记误当作普通数据页写入
5. 调用 `file.flush()`

### 6.2 页面分配

分配页面时优先复用空闲页：

```text
if free_list_head != -1:
    page_id = free_list_head
    free_list_head = 释放页中保存的下一个页号
else:
    page_id = page_count
    page_count += 1
```

复用页面会先清零；新增长页直接追加到文件末尾。分配后会维护内存中的空闲页集合，并在正常关闭时将元数据写回。

### 6.3 页面释放

释放页面时，页面前 8 字节写入专用的 `FREE` 标记和旧的空闲链表头，然后把当前页设置为新的链表头：

```text
被释放页的前 4 字节 = `FREE`
被释放页的后 4 字节 = old_free_list_head
free_list_head      = 当前被释放页
```

因此空闲页链表是一个保存在磁盘页面内部的单向链表。打开文件时会遍历并校验该链，检测越界、重复释放和成环问题；读取或再次释放已释放页都会失败。

## 7. 缓冲池管理

### 7.1 缓冲池数据结构

`BufferPoolManager` 使用一个字典保存内存中的页面：

```python
frames: dict[page_id, Page]
```

缓冲池容量由 `pool_size` 决定。每个页面有 `pin_count`：

- `pin_count > 0`：页面正在使用，不能被淘汰
- `pin_count == 0`：页面可以进入淘汰候选集合

### 7.2 获取页面

`get_page(page_id)` 实际上是 `fetch_page(page_id)` 的别名。

页面获取流程：

```text
1. 在 frames 中查找 page_id
2. 找到：命中计数 +1，pin_count +1
3. 找不到：未命中计数 +1
4. 如果缓冲池已满，先淘汰一个未 pinned 页面
5. 从 DiskManager 读取页面
6. 放入 frames，设置 pin_count = 1
```

系统会统计：

- hits
- misses
- accesses
- hit_rate
- evictions
- disk_reads
- disk_writes

### 7.3 释放页面和 dirty 标记

调用方完成页面操作后必须调用：

```python
buffer.unpin_page(page_id, is_dirty=True_or_False)
```

该操作会减少 `pin_count`。当 `pin_count` 变为 0 时，页面进入替换器的候选集合。如果本次操作修改了页面，则设置 `dirty = True`。

### 7.4 LRU 和 FIFO

当前实现支持两种替换器：

- LRU：页面最后一次变为可替换时进入队尾，队首是最久未使用页面。
- FIFO：页面第一次进入可替换集合时记录序号，命中不会改变该序号。

页面被重新 pin 时会从 LRU 候选集合中移除；FIFO 则保留原始进入顺序。

可以运行时调用：

```python
buffer.set_policy("LRU")
buffer.set_policy("FIFO")
```

切换策略后，当前未 pinned 页面会重新加入新的替换器。

### 7.5 页面淘汰

淘汰过程如下：

```text
1. 按当前策略取得候选页面顺序
2. 跳过 pin_count > 0 的页面
3. 找到第一个可淘汰页面
4. 如果页面 dirty，先写回磁盘
5. 从 frames 和替换器中移除页面
6. 增加淘汰计数并写入替换日志
```

普通页面获取或新建时，如果所有帧都 pinned，则页面无法装入普通缓冲帧，会抛出：

```text
StorageError: buffer pool is full: all frames are pinned
```

### 7.6 新建和刷盘

`new_page()` 的返回页面初始为 pinned，调用方需要随后 unpin。为了只申请页号，当前还提供 `new_page_unpinned()`。

当 `new_page_unpinned()` 发现所有已有帧都 pinned 时，会走“直接落盘”兜底路径：分配并初始化磁盘页，写盘后只返回页号，不把页面放入缓冲池。这条路径专门解决 `pool_size=1` 时表页扩展与当前页仍被引用之间的冲突；调用方后续仍可通过 `fetch_page()` 重新获取该页。

`flush_page(page_id)` 只对 dirty 页面写盘并清除 dirty 标记；`flush_all()` 刷新缓冲池中的所有 dirty 页面。

替换日志保存在有界内存列表中，记录命中、未命中、读盘、写盘、淘汰和直接落盘等事件，避免长期运行导致日志无限增长。

## 8. 表到页面的映射

### 8.1 TableHeap

一张表由 `TableHeap` 表示，表的根页号保存在 Catalog 的 `TableSchema.root_page_id` 中。

每个数据页的页头保存下一页页号：

```text
root_page → data_page_2 → data_page_3 → ... → -1
```

### 8.2 插入一行

`TableHeap.insert_row(values)` 的处理流程：

```text
1. encode_row(values)
2. 从根页开始逐页获取
3. 如果当前页有空间，插入记录并返回 RowId
4. 如果当前页已满且没有下一页：
   a. 分配新数据页
   b. 修改当前页的 next_page_id
   c. 将新页作为下一页
5. 继续向新页插入
```

返回的 `RowId(page_id, slot_id)` 是记录的物理位置。

### 8.3 顺序扫描

`iter_rows()` 从根页开始沿 `next_page_id` 遍历所有数据页，再逐个检查槽位：

- 已删除槽位跳过
- 有效槽位读取二进制记录
- 调用 `decode_row()` 还原成 Python 值
- 返回 `(RowId, values)`

这就是 `SeqScan` 执行算子的物理基础。

### 8.4 删除表和页面回收

`drop_all()` 沿页面链表遍历所有页面，对每个页面执行：

1. 读取下一页页号
2. unpin 当前页
3. 从缓冲池移除页面
4. 交给 DiskManager 加入空闲页链表

因此 DROP TABLE 后，表占用的页面可以被后续新表复用。

## 9. 记录序列化

记录不直接保存 Python 对象，而是保存紧凑的二进制格式：

```text
row := uint16 column_count | value × column_count
```

值采用标签加数据体：

| 标签 | 类型 | 数据格式 |
|---:|---|---|
| 0 | NULL | 无数据体 |
| 1 | INT | int32，小端 |
| 2 | VARCHAR | uint16 字节长度 + UTF-8 字节 |
| 3 | BOOL | uint8，0 或 1 |

该格式使页面层不需要理解 SQL 类型，只需要保存一段字节。类型语义由 SQL 编译器和执行器负责。

当前实现要求单行记录能够放入一个页面，不支持跨页记录。

## 10. Catalog 的页式持久化

系统目录不是单独使用内存字典保存，而是也存储在页面中：

- Catalog 页类型为 `PageType.CATALOG`
- Catalog 根页号保存在元数据页的 `catalog_root`
- Catalog 记录使用和普通数据相同的槽位页格式和 Row 编码

保存 Catalog 时，当前实现采用整体重写策略：

```text
1. 释放旧 Catalog 页链
2. 分配新的 CATALOG 根页
3. 将 Catalog 中的所有列描述写入新页链
4. 更新 meta.catalog_root
```

启动时读取 `catalog_root`，扫描 Catalog 页链，再由这些行重建内存中的 `Catalog`。

这种实现简单、容易验证，但每次建表或删表都需要重写整个目录。

## 11. 一次 INSERT 的完整数据流

```text
INSERT SQL
   │
   ▼
Semantic / Planner 生成 InsertPlan
   │
   ▼
InsertExecutor 计算 Python 值
   │
   ▼
TableHeap.insert_row()
   │
   ├─ encode_row()
   ├─ BufferPoolManager.fetch_page()
   ├─ Page.can_insert()
   ├─ Page.insert_record()
   └─ unpin_page(dirty=True)
          │
          ▼
     flush_page / flush_all
          │
          ▼
       DiskManager.write_page()
```

一个页面从磁盘进入内存、被修改、最终写回磁盘的过程，可以概括为：

```text
磁盘页 → fetch_page → Page 对象 → 修改并 dirty
       → unpin_page → flush 或淘汰时写回 → 磁盘页
```

## 12. 当前实现的核心不变量

技术人员维护代码时应保持以下不变量：

1. 普通磁盘页读写长度必须始终等于 `PAGE_SIZE`。
2. 页号 0 只能作为元数据页使用。
3. 被 pinned 的页面不能被淘汰。
4. dirty 页面从缓冲池淘汰前必须写回磁盘。
5. 页面离开缓冲池后，替换器不能继续保留该页面的候选记录。
6. 表的根页和后续页必须形成以 `INVALID_PAGE_ID` 结尾的有效链表。
7. Catalog 的根页号必须与元数据页中的 `catalog_root` 一致。
8. 释放页必须进入空闲页链表，重新分配时不能重复分配仍在使用的页。
9. 页面被获取后必须有匹配的 unpin，避免 pin 泄漏。
10. 修改页面后必须传递 `is_dirty=True`，否则修改可能不会持久化。

## 15. 已知限制和需要重点关注的问题

### 14.1 持久化属于正常关闭场景，不提供崩溃恢复

当前系统通过 `flush_all()` 和文件 `flush()` 保证正常执行结束或调用 `close()` 后的数据落盘，但没有：

- WAL
- redo/undo 日志
- checkpoint
- 原子提交
- 崩溃恢复

因此不能把“已经调用 flush”理解为完整的数据库崩溃一致性保证。

### 14.2 删除只回收槽位，不整理页内碎片

删除记录后，槽位可以复用，但原记录区空间不会合并。长期频繁删除和插入不同长度记录时，页面可能出现无法有效利用的碎片。

### 14.3 单行记录不能跨页

当前一条序列化记录必须完整放入单个页面。超长 VARCHAR 或超大行会被拒绝，不支持溢出页或大对象存储。

### 14.4 Catalog 的扩展约束字段保存不完整

当前 Catalog 持久化保存了表名、列名、类型、NOT NULL、PK 和根页号，但没有保存 UNIQUE 和 DEFAULT。若这些扩展约束需要在重启后继续生效，应扩展 Catalog 行格式。

### 14.5 当前没有并发控制

实现面向单进程、单线程使用，没有文件锁、页面锁或并发访问控制。这不属于当前指导书要求的最小页式存储功能，但不能直接用于多线程或多进程数据库服务。

## 16. 与项目要求的对照

| 文档要求 | 当前实现 |
|---|---|
| 固定大小页面 | 已实现，页面大小为 4096 字节 |
| 页编号唯一 | 已实现，页号对应文件中的固定位置 |
| 页分配和释放 | 已实现，支持空闲页链表 |
| 页读写接口 | 已实现 `read_page()` / `write_page()` |
| 页缓存 | 已实现固定帧缓冲池 |
| LRU/FIFO | 已实现并可切换 |
| 命中统计 | 已实现命中、未命中、命中率、读写次数、淘汰次数 |
| 替换日志 | 已实现内存日志，并可通过 CLI 查看 |
| 表到页集合映射 | 已实现 TableHeap 页链表 |
| Row/Page 映射 | 已实现二进制序列化和槽位地址 |
| 空闲页管理 | 已实现分配、释放和复用 |
| 数据库集成 | 已实现执行器通过 TableHeap 和 BufferPool 访问页面 |

总体上，当前实现已经形成了完整的“文件 → 页面 → 缓冲池 → 表页链 → 执行器”存储闭环，满足简化数据库的核心页式存储要求。单帧缓冲池扩展和 pinned 页删除异常路径已经补齐；后续若继续增强，优先考虑页内碎片整理、Catalog 约束字段持久化以及崩溃恢复。
